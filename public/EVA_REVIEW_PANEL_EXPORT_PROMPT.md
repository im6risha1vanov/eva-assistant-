# Задание Codex: реальные диалоги для закрытой панели Евы

Работаем с существующим проектом Ева. Подготовь read-only экспорт клиентской истории и LLM-разборов для закрытой панели «Диалог в контексте». Не меняй webhook, сервисы, клиентский режим и не отправляй сообщения клиентам. Сохрани текущие изменения разработчиков.

Панель: https://eva-dialogue-review.im6risha1vanov.chatgpt.site . Образец JSON доступен по пути /dialogues-example.json. В образце все диалоги вымышленные; не используй их как сведения о школе или как оценку качества модели.

Сначала прочитай AGENTS.md, PROJECT_STATE.md и существующие материалы исследования среды/книги продаж. Сверь текущие пути: сервер root@176.53.161.160, приложение ранее /opt/eva, данные ранее /var/lib/eva. При локальном запуске Codex на Windows используй SSH; не выполняй команды Ubuntu локально.

1. Определи, где доступна история обеих сторон: клиента и администратора. Одна таблица входящих webhook не является полным диалогом. Используй подтверждённый API или официальный экспорт AlfaCRM/Wazzup соответствующей версии. Не считай отсутствие событий доказательством отсутствия ответов. Зафиксируй момент среза, филиалы, каналы, периоды, реальные количества и ограничения полноты. Секреты не печатай.
2. Выгрузи доступные диалоги в хронологическом порядке, с устойчивыми ID и направлением сообщений. Для первого пакета возьми доступные недавние случаи разных смысловых групп; размер до 3 МБ, до 300 диалогов, до 600 сообщений на диалог. При больших объёмах дели на пакеты и сохраняй журнал охвата. Не обрезай незаметно начало длинного диалога: явно history_complete=false и history_note с диапазоном/причиной. Приватные выгрузки не включай в Git, логи и публичные URL.
3. Для содержательных клиентских сообщений подготовь вариант ответа на основе реальной книги продаж и подтверждённых данных. Предпочтение владельца — GPT-6 Luna; проверь реальное API-подключение, лимиты и стоимость, не заимствуй токены Codex. Каждый вариант — только черновик администратору, без отправки. Все изменения сценариев требуют согласования владельца.
4. При историческом разборе LLM должна видеть только переписку до выбранного сообщения включительно. Не передавай ей фактический последующий ответ администратора или более поздние реплики. Временные факты CRM из сегодняшнего дня не выдавай за известные на исторический момент: пометь неизвестные факты. Фактический ответ администратора сохраняй отдельно как сообщение истории для сравнения на сайте.
5. Реально переданные модели ID сообщений запиши в used_message_ids. Не ставь все ID автоматически, если часть истории не поместилась в контекст; фиксируй реальный состав. Изоляция диалогов, отсутствие будущих сообщений и действие регламента важнее красивого черновика.

Формат пакета:

```json
{
  "schema_version": 1,
  "source": {
    "label": "Источник и диапазон выгрузки",
    "is_demo": false,
    "exported_at": "2026-10-17T14:00:00+03:00",
    "coverage_note": "Реальный охват, недоступные каналы/периоды и причины"
  },
  "dialogues": [{
    "id": "stable-dialogue-id",
    "customer_label": "Псевдоним клиента",
    "title": "Короткое название ситуации",
    "topic": "Пропуски",
    "channel": "MAX",
    "branch": "Подтверждённый филиал или Не определён",
    "summary": "Краткая предыстория для владельца. Она не заменяет исходные сообщения.",
    "history_complete": false,
    "history_note": "Причина и диапазон доступности истории",
    "messages": [
      {"id":"m1","role":"client","text":"Текст клиента","at":"2026-10-17T10:00:00+03:00"},
      {"id":"m2","role":"admin","text":"Фактический ответ сотрудника","at":"2026-10-17T10:05:00+03:00"}
    ],
    "analyses": [{
      "client_message_id": "m1",
      "draft": "Подготовленный моделью черновик",
      "intent": "Понятая суть вопроса в контексте",
      "explanation": "Краткое обоснование без скрытых рассуждений",
      "known_facts": ["Факт с источником/автором"],
      "missing_facts": ["Что не подтверждено"],
      "required_actions": ["Что нужно реально сделать; действие ещё не исполнено"],
      "rule_refs": [{"title":"Правило","source":"Версия книги, вкладка/диапазон или rule_id","status":"verified"}],
      "used_message_ids": ["m1"],
      "model": "Фактически использованный model_id",
      "generated_at": "2026-10-17T14:00:00+03:00"
    }]
  }]
}
```

source.is_demo=true обязательно для учебных/синтетических пакетов; они не должны выдаваться за реальную CRM-историю.

Допустимые role: client/admin/system. Вложения передавай как attachments: [{name,type}], не как публичные ссылки с секретами. Если распознавания не было, не считай содержимое вложения прочитанным. Время — ISO 8601 с часовым поясом. ID сообщений уникальны внутри диалога. ID диалогов уникальны в пакете. Одно analysis на одно client_message_id. used_message_ids ссылаются только на существующие сообщения до этого client_message_id включительно. crm_url необязателен, допускается только https://kodologiyapiksel.s20.online без встроенных credentials. Статус verified допустим лишь при реальной проверке источника; proposed — предложение, unknown — неизвестно.

Сохрани пакет в закрытом рабочем каталоге данных и сообщи путь, число диалогов/сообщений/LLM-разборов и неполные истории. Подготовь команду scp для скачивания владельцем на Windows. Не загружай историю на сайт несуществующим API и не помещай токены в браузер. Владелец импортирует JSON через кнопку «Загрузить диалоги».

Проверь: отсутствие секретов в экспорте, порядок времени, реальные направления, ссылочную целостность, отсутствие будущих реплик в модельном контексте, отсутствие тестовых отправок и корректный режим draft.

После работы на сайте владелец скачает eva-corrections-*.json. Он содержит оценки, общие предпочтения и предложения с proposed/approved. Учебные оценки (demo_dataset=true) не выдавай за реальные случаи. Согласованные предложения подготовь как diff новой версии сценариев, проведи регрессионные тесты и зафиксируй статус внедрения. Сам экспорт не разрешает включать клиентскую автоотправку; согласование черновика ответа не утверждает новое бизнес-правило.
